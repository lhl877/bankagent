1.3 架构上最关键的一条约束

bank/core.py 模块文档（L21-L28）写明：

所有资金变动只能走 transfer() / reverse() 这两个入口。
权限引擎和 Agent 都不允许直接写 accounts.balance。
原因：「权限分级」如果只做在对话层，一句精心构造的 prompt 就能绕过。
分级必须作用在不可绕过的执行入口上，而不是"Agent 的自觉"。

这条约束的实际成立范围是：资金类操作（余额增减）确实唯一走 transfer()/reverse()。 但非资金类写操作绕过了核心，见 §6.2。

2. 核心算法说明

2.1 权限分级动态抬级（含日累计判定）

代码位置：security/permissions.py → check_tier()（L108）、SMALL_TRANSFER_CAP（L51）、ACTIONS（L55）、DEFAULT_TIER（L87）

分级注册表

操作按基准级别登记在 ACTIONS 字典中，共 22 项（实测 len(ACTIONS) == 22）。实际内容：

级别 操作数 操作清单
绿色（自动执行） 9 account.balance 查询余额、account.list 查询账户列表、account.find_contact 查找收款人、tx.list 查询交易记录、bill.analyze 账单分析、bill.anomaly 异常交易识别、wealth.list 查询理财产品、wealth.holdings 查询持仓与收益、subscription.list 查询订阅与代扣
黄色（用户确认） 5 transfer.small 小额转账、transfer.scheduled 定时转账、split.request 发起 AA 收款、subscription.cancel 取消订阅、card.apply_virtual 申请虚拟卡
红色（强验证） 8 transfer.large 大额转账、wealth.purchase 申购理财、wealth.redeem 赎回理财、card.limit_change 调整卡额度、card.freeze 挂失/冻结卡片、card.unfreeze 卡片解挂、password.change 修改密码、card.unlock_limit 解除交易限制

22 项中有 2 项目前不可达（登记了但没有任何意图映射到它，或已被显式拒绝）： transfer.scheduled（被显式拒绝，见 §2.1.5）与 card.unlock_limit（无意图映射）。 因此实际可执行的操作为 20 项。

动态抬级算法

ACTIONS 里登记的是基准级别。转账类操作的实际级别由金额与当日累计共同决定：

输入：action, params{amount}, core, acct_id

1. 若 action 不属于 {transfer.small, transfer.large, transfer.scheduled}
      → 直接采用注册表基准级别，结束

2. amount = params.amount
   若 amount ≤ 0:
      → 保持基准级别，理由「金额尚未确定」
        （执行阶段会重算，见 2.5）

3. 若 amount > SMALL_TRANSFER_CAP (100000 分 = 1000 元)
      → tier = RED
      → 理由「单笔 X 元 > 1000 元，超出小额上限」

4. 否则（单笔未超限）：
      used      = core.daily_outgoing(acct_id)      ← 关键：查当日已转出总额
      projected = used + amount
      若 projected > SMALL_TRANSFER_CAP:
          → tier = RED
          → 理由「今日已转出 used 元，加上本笔将达 projected 元，超出小额上限」
      否则:
          → tier = YELLOW
          → 理由「今日已转出 used 元，本笔后累计 projected 元，在小额上限内」

5. needs = {GREEN: [], YELLOW: ['user_confirmation'],
            RED: ['user_confirmation','strong_verification']}[tier]

6. 返回 {tier, action, desc, reasons[], needs[], dynamic}

为什么必须看日累计，而不是只看单笔

这是本算法唯一真正重要的设计判断。若只判单笔：

想转 2000 元 → 拆成 3 笔 700 元 → 每笔都 ≤ 1000 元 → 每笔都是黄色 → 完全绕开强验证

只看单笔的实现在演示时"看起来没问题"，因为每一笔的处理都符合规则； 问题出在规则的作用对象错了：它约束的是一笔交易，而攻击者操作的是一个会话。

daily_outgoing()（bank/core.py L215）的查询条件是 from_acct=? AND status='succeeded' AND created_at>=当日零点， 即已冲正的交易不计入累计（用户被撤销的转账不应继续占用额度）。

未登记动作的处理

DEFAULT_TIER = RED（L87）。未在 ACTIONS 中登记的动作按红色处理并附加 「默认拒绝原则」理由。这一点值得强调：很多演示系统会把未登记动作按绿色放行， 那等于"没写规则的地方没有权限约束"。本项目采用相反的默认值。

2.1.5 定时转账：显式拒绝，而非静默降级（一次真实修复）

这一节记录一个语义陷阱及其修复，因为它是本项目里最容易被忽略、 后果却最直接的一类问题。

修复前的行为：IntentParser 能识别「明天 / 每月 / 预约」等时间词并置位 slots['scheduled'] = True，但调度器从未实现。当时 _dispatch() 把 transfer.small / transfer.large / transfer.scheduled 归入同一分支， 因此：

用户：「每月给李娜转 500 元」
系统：识别为 transfer（意图识别是对的）→ 分级黄色 → 确认卡 → 执行
结果：500 元**立刻**转出

用户以为设了一个每月自动转账，实际钱当场就出去了 —— 语义完全相反， 且属于资金损失。这是"功能未实现"里最危险的一种：不是报错， 而是以一个看起来合理的形状做了完全不同的事。

修复方式：显式拒绝，不做静默降级（propose() 中，位于缺槽位检查之后）：

if intent.slots.get('scheduled'):
    self.audit.append('guard.unsupported_scheduled', session_id=self.id,
                      text=text[:120])
    return {'type': 'refused',
            'message': '定时/预约转账目前还没有实现调度器，我不能受理。\n\n'
                       '**我不会把它当成立即转账执行** —— 那样你的钱会马上出去，'
                       '和你说的「每月」完全不是一回事。\n\n'
                       '如果这笔钱现在就要转，请去掉时间词重说一次，'
                       '例如「给李娜转 500 元」，我会先给你明细让你确认。'}

代码注释（L201-208）记录了选择理由：

所以这里宁可明确说"不支持"，也不做静默降级。
赛题允许覆盖部分场景，不允许骗用户。

实测确认（三种定时说法、三种不同时间词）：

输入 propose 返回 余额变动
每月给李娜转 500 元 refused 无
明天给王强转 300 元 refused 无
预约下周给李娜转 100 元 refused 无

三条均写入审计事件 guard.unsupported_scheduled（实测 3 条，链完整）。

修复后的影响：

  • 定时转账从"静默错执行"变为"明确不受理"，语义风险消除
  • ACTIONS 中的 transfer.scheduled 登记项仍然不可达（INTENT_ACTION['transfer']

恒为 transfer.small，且带 scheduled 的意图已在更早处被拒绝）， 属于登记表与实现的残留不一致

  • 赛题「智能转账」场景中的定时转账能力仍未实现（见 §5.11）
这个案例值得单独强调："未实现"应当显式失败。 若一个功能没有实现，
正确做法是拒绝并说明，而不是让它以另一种语义"成功"。
前者用户会去别处办，后者用户会在不知情的情况下损失资金。

2.2 确认凭证绑定 payload_hash

代码位置：security/permissions.py → payload_hash()（L91）、ConfirmationStore.issue()（L200）、.peek()（L212）、.consume()（L238）

要防的攻击

① 用户对一笔 100 元转账点了「确认」→ 系统签发凭证 T
② 攻击者截获 T
③ 攻击者提交：op_id 不变，金额改成 10000 元，带上 T
④ 若系统只看「T 是否有效」→ 转账成功

问题在于凭证只证明了"用户确认过某件事"，没有证明"现在要执行的这件事就是他确认的那件"。

算法

规范化哈希（payload_hash）：

clean     = {k: v for k, v in params.items()
             if k not in ('idem_key', 'confirmed_at', 'nonce', 'ts')}
canonical = json.dumps({'action': action, 'params': clean},
                       sort_keys=True, ensure_ascii=False,
                       separators=(',', ':'))          # 紧凑、键有序
return sha256(canonical.encode('utf-8')).hexdigest()

两条性质必须同时成立：

  • 相同内容 → 相同哈希：否则用户正常确认也会失败（假阴性）
  • 内容不同 → 哈希必不相同：否则可以改参数重放（假阳性）

sort_keys=True 保证键序无关；排除 nonce/ts/idem_key 使哈希与无关字段解耦。

凭证结构（issue）：

token = secrets.token_urlsafe(24)          # 192 bit 随机
_store[token] = {
    'session':      session_id,             # 绑定会话
    'action':       action,                 # 绑定动作
    'payload_hash': payload_hash(action, params),   # 绑定内容
    'issued_at':    time.time(),            # 时效起点
    'used':         False,                  # 一次性标记
}

四重校验（peek）：存在性 → 未使用 → 会话匹配 → 未超时 → 动作匹配 → hmac.compare_digest 比对 payload_hash。 使用 compare_digest 而非 == 是为了避免哈希比较的时序侧信道。

peek / consume 拆分（一次真实修复）

初始实现只有一个 verify_and_consume()，在红级流程中位于短信验证之前。后果：

  1. 用户验证码输错一次 → 确认凭证已被标记 used → 必须从头重新发起
  2. 更严重：攻击者拿到凭证后故意提交错误验证码，即可让合法用户的凭证作废 —— 拒绝服务

修复为两阶段：

peek(token, ...)     只查资格，不写状态          → execute() 开头调用
   ...（中间做重算分级、短信验证码校验）...
consume(token)       全部通过后才标记 used=True   → 紧邻 _dispatch() 之前调用

verify_and_consume() 保留给黄级（无强验证）使用，内部即 peek + consume。

为什么需要

赛题要求「生成的代码在受限、可监控的逻辑隔离环境中运行」。 本系统允许 Agent 计算金额表达式（例如 AA 收款「240 元 3 人平摊」）， 因此需要一个能安全求值算术表达式、但不能执行任意代码的机制。

设计立场：白名单，不是黑名单

黑名单（禁用 eval、exec、__import__、os…）永远会漏 —— Python 的 属性链、getattr 拼接、编码变形等手段太多。本项目采用白名单： 解析成 AST 后，只有列在 _ALLOWED_NODES 里的节点类型才被放行， 任何不在表中的节点直接抛 SandboxError。

_ALLOWED_NODES = (
    ast.Expression, ast.BinOp, ast.UnaryOp, ast.Constant,
    ast.Add, ast.Sub, ast.Mult, ast.Div, ast.FloorDiv, ast.Mod,
    ast.USub, ast.UAdd, ast.Pow, ast.Tuple,
)

被结构性拒绝的节点（未列入白名单即为拒绝）： Call（函数调用）、Attribute（属性访问）、Subscript（下标）、Name（变量）、 Import/ImportFrom、Lambda、Compare、BoolOp、IfExp、ListComp/ DictComp/SetComp/GeneratorExp、JoinedStr（f-string）、Await 等。

嵌套深度 ≤ 12 层 防止深递归

幂指数 |r| ≤ 8 防止计算爆炸（9**9**9 会耗尽内存/CPU）

2.4 审计哈希链

代码位置：security/audit.py → AuditLog（L27）、append()（L42）、_digest()（L66）、verify_chain()（L73）

要防的问题

赛题要求「所有关键操作需记录完整的决策链路与执行日志」。 但普通追加日志有个被忽略的前提：日志本身可被修改。 若攻击者获得写权限后删除或改写自己的痕迹，"完整日志"就不完整了。

算法

每条记录的哈希覆盖上一条的哈希，形成链：

genesis = "0" * 64
对第 i 条记录：
    body = {seq, at, event, session, fields, prev: hash(i-1)}
    hash(i) = SHA256( json.dumps(body, sort_keys=True,
                                 ensure_ascii=False,
                                 separators=(',',':')) )

校验时从 genesis 开始逐条重算：

def verify_chain(self):
    prev = GENESIS
    for i, e in enumerate(self._entries):
        if e['prev'] != prev:
            return False, '第 %d 条记录的前序哈希不匹配（记录被删除或插入）' % i, i
        if self._digest(e) != e['hash']:
            return False, '第 %d 条记录的内容被修改过' % i, i
        prev = e['hash']
    return True, '哈希链完整，共 %d 条记录' % len(self._entries), None

链式结构带来的性质：

  • 改内容 → 该条 _digest(e) != e['hash'] → 定位到具体序号
  • 删记录 → 其后一条的 prev 指向已不存在的哈希 → 定位到断点
  • 插入记录 → 同理断链
  • 改内容并重算该条哈希 → 下一条的 prev 对不上 → 仍然暴露

局限：哈希链不防"整链重写"（攻击者有完全写权限时可从头重算整条链）， 也不防"删除尾部若干条"。这些需要 WORM 存储或外部锚定，属已知不足（§5.4）。

2.5 两阶段执行：执行前重算分级

这是分级机制能否真正成立的关键，独立成节说明。

阶段一 propose(text)                      阶段二 execute(op_id, token, otp...)
─────────────────────────────            ─────────────────────────────────
熔断检查                                  peek(token) 校验凭证（不消费）
detect_injection(text)   → 可审计事件      ← 重算 check_tier() 并比较

execute() 中的重算与升级分支（原文）：

tier_now = check_tier(op.action, op.params, self.core, params.get('acct'))
if tier_now['tier'] != op.tier_info['tier']:
    self.audit.append('tier.escalated', ...)
    if tier_now['tier'] == RED and op.tier_info['tier'] == YELLOW:
        op.tier_info = tier_now
        new_token = self.confirm.issue(self.id, op.action, op.params)
        return {'type': 'tier_escalated',
                'message': '在你确认期间，该操作的风险等级已上升为「红色 · 需强验证」…',
                'requires_strong': True, ...}
    # 其他变化方向：直接中止
    return {'type': 'refused',
            'message': '该操作的风险等级在确认期间发生了变化，为安全起见已中止。'}

为什么不能复用阶段一的结论：用户从"发起"到"确认"之间有时间差。 若这期间该账户已经转过几笔，日累计可能已越过 1000 元阈值。 此时阶段一算出的"黄色"已失效，若继续沿用，这个时间差就是越权窗口。

注意重算的分级只用结构化参数（op.action、op.params）， 用户原始文本不参与，所以模型或用户都无法影响这次判定。

3.2.6 关于一条刻意不拦的载荷

这个取舍不降低安全性，理由正是 §3.2.5：该输入因缺少明确金额 而落在 clarify，不会执行。删除该规则只是少了一次"留痕"事件， 没有放宽任何权限。

5. 已知边界与不足

以下均为真实存在的限制，不作淡化。这是演示项目，不是生产系统。

5.1 无身份认证与授权

事实：api_server.py 没有任何认证。get_session(sid)（L57）直接用客户端传来的 session_id 创建或复用会话 —— 任何人只要构造 POST /api/chat {"session":"任意值"} 即可获得一个会话，并且可以看到该 session_id 对应的审计记录与待确认操作。

影响：

  • 演示环境可接受（本地运行、无真实资金）
  • 真实场景下这是根本性缺陷：会话 ID 即身份，且可猜测/枚举
  • 会话之间的隔离完全依赖 session_id 的随机性，而它由客户端自由指定

建议：接入真实身份体系（OAuth2/OIDC），服务端签发不可伪造的会话令牌 （HttpOnly Cookie 或签名 JWT），会话与用户强绑定，并对所有 /api/* 做鉴权。

5.2 熔断与凭证可被绕过（会话 ID 可任意指定）

事实：CircuitBreaker 的锁定键是 session_id，而 session_id 由客户端提供。 攻击者每次请求换一个 session_id 即可无限重试，熔断计数永远从零开始。

影响：熔断在"攻击者配合"的前提下基本无效。它挡得住自动化脚本的粗心实现， 挡不住有意规避者。

建议：熔断键改为服务端可识别的稳定标识（用户 ID / IP / 设备指纹）， 并对同一身份做跨会话累计。同时补速率限制（见 5.3）。

5.3 无速率限制

事实：ThreadingHTTPServer 之上没有任何限流。/api/chat、/api/execute、 /api/verify/request 均可被高频调用。

具体风险：/api/verify/request 可被反复调用以批量签发短信验证码。 虽然单个 challenge 有 5 次尝试上限（见 §5.7），但挑战本身可以无限量申请。

影响：真实环境中等于短信轰炸 + 成本放大 + 暴力破解面扩大。

建议：按用户/IP 限制 /api/verify/request 调用频率（如 1 次/分钟、 5 次/日），失败累计后指数退避。

5.4 审计日志单机存储、无 WORM、可整链重写

事实：AuditLog 追加写本地文件 audit.log，并同时持有内存 _entries。 哈希链能检测单点篡改与删除（§2.4 已验证），但：

  • 有文件写权限者可删除尾部记录（链仍然自洽，因为没人指向被删部分）
  • 有文件写权限者可重算整条链并从第 0 条替换
  • 无异地副本，文件损坏即丢失

影响：审计的"防篡改"是单机内相对的，不是对抗有写权限攻击者的绝对保证。

建议：写入独立权限域的 WORM 存储；定期把链尾哈希锚定到外部 （签名时间戳服务、另一系统、或链上）；审计写入与业务写入使用不同凭证。

5.5 确认凭证与 OTP 存于进程内存

事实：ConfirmationStore._store 与 ._otp 是普通 dict（L194、L197）。 docstring 自述：「进程内存储即可：演示系统单进程运行。真实系统要放 Redis 之类的共享存储（多实例部署时需要），并且要用 HMAC 签名而不是只存内存里的随机串。」

影响：重启即全部失效（演示环境可接受）；多实例部署时凭证无法跨实例校验； 内存增长无上限（_prune() 仅在 issue() 时触发，见 §5.8）。

建议：迁至 Redis 等共享存储；凭证本身用 HMAC 签名，使服务端可无状态校验。

5.6 熔断与锁定状态未被审计为可查询的完整事件流

事实：CircuitBreaker._events 记录了锁定事件，但该列表没有任何接口暴露， 也不随会话清理重置以外的路径持久化。

影响：锁定发生了但无法通过 /api/audit 查询到 _events 的内容 （breaker.blocked 会进审计，但 record_failure 里 _events.append 的那条 "LOCKED / 窗口内失败 N 次"不会）。答辩时无法直接展示"谁在什么时间被锁了多少次"。

建议：把 _events 的内容也写入 AuditLog，使锁定成为可检索事件。

5.7 意图解析基于正则，非 LLM，存在误抽与覆盖不足

事实：IntentParser.parse()（L217）用正则与关键词匹配，docstring 说明这是 刻意的选择（「可测试、可离线、判定稳定」），并注明生产系统可接 LLM 兜底。

实测发现的具体缺陷：

  • 输入「有哪些理财产品可以买」→ 返回 clarify（而非执行 wealth.list）
  • 「把 A004 的余额全部转给我」→ 注入检测未命中，属刻意设计（§3.2.6 说明原因）
  • 金额抽取要求显式钱标记（元/块/圆），省略说法「转五百」会被追问一次

（这是刻意的取舍，见 §5.7.1）

影响：功能覆盖率与首轮命中率受限。但不影响安全性 —— 解析失败走 clarify（追问），解析错误走确认卡（用户可见明细）。 权限判定不依赖解析器，所以解析器的缺陷不会变成越权。

建议：接 LLM 作为兜底解析器，但保持权限判定不读 LLM 输出 （即：LLM 可以帮忙把话听懂，但不能决定风险等级）。

5.7.1 金额解析：从"猜"改为"要求显式标记"（一次完整修复）

中文金额解析经历了一次完整的踩坑与重构，过程本身值得记录。

重构前的实际错误（会造成真实金额错误且不报错）：

输入 旧实现返回 应为 后果
给李娜转五百 5.0 500 "百"被丢弃，用户说 500 元、系统转 5 元
给李娜转两块五 2.0 2.5 小数部分丢失

两次错误都不报错，金额合法地通过了所有校验 —— 是最危险的一类缺陷。

根因：_cn_small 未正确进位百/千；且无法可靠区分 「三百五」（金额）与「第一次」（序数）这类字面相同的表述。

最终方案：要求显式的钱标记（元/块/圆），歧义随之消失。

_CN_AMOUNT_RE  = re.compile(r'([零一两二三四五六七八九十百千]{1,10})\s*(元|块|圆)')
_CN_MULT_RE    = re.compile(r'([一两二三四五六七八九十])\s*(万|千)')     # 倍数本身明确
_CN_DECIMAL_RE = re.compile(r'([一两二三四五六七八九十])\s*(?:块|元|圆)\s*([零一两二三四五六七八九])\s*(?:毛|角)?')

取舍：「转五百」（无"元"字）返回 None，会被追问一次。 代码注释记录了理由：

代价是「转五百」这种省略说法必须追问一次；
但金额猜错的代价（转 5 元 vs 转 500 元）远高于多问一句。

实测：11 条金额用例中 10 条正确、8 条非金额文本全部正确返回 None （含「调一下额度」「第一次转账」「把A004的钱转给A001」）。 1 条不符预期，见 §6.6（「三百五元」→ 305 而非 350）。

5.7.2 账号干扰的擦除（一次"静默失效"的修复）

parse_amount_yuan() 需要先擦掉账号、日期等"看起来像数字"的干扰， 否则「把A004的钱转给A001」里的 4 会被当成金额。

原实现用了 \b 词边界，但它从未生效：

scrub = re.sub(r'\bA0*\d+\b', ' ', text)     # ✗ 永远匹配不上

原因：中文也是"word 字符"，因此在「把A004」中 A 前面 没有词边界，\b 断言失败，整个替换静默不执行。

修复（去掉 \b）：

scrub = re.sub(r'A0*\d+', ' ', text, flags=re.I)

实测：parse_amount_yuan('把A004的钱转给A001') → None（不再抠出 4.0）。

这个案例的教训：\b 是按英文的词边界语义设计的，
中文文本里大量"中英数字相连"的场景下它不成立。
依赖 \b 做边界锚定的正则，在中英混排文本上必须逐例验证，
否则会像本例一样静默失效——不报错，只是不生效。

5.8 pending 与凭证字典无独立淘汰机制

事实：

  • AgentSession.pending（L129）只在成功执行时 pop。用户发起后放弃的操作

（关页面、点取消以外的路径）会一直留在内存

  • ConfirmationStore._store 与 _otp 的清理仅发生在 issue() / issue_otp()

调用时（_prune()，L302），若长期无人 issue 则过期记录不释放

  • AgentSession.pending 与凭证 TTL 不联动：凭证 180 秒后失效，

但对应 PendingOperation 仍在 pending 里，execute() 会先因凭证失效而拒绝

影响：长时运行内存缓慢增长；由于是演示单进程，实际影响有限。

建议：给 pending 加 TTL 或容量上限，在 propose()/execute() 时惰性清理； 把凭证 TTL 与 pending 生命周期统一。

5.9 测试覆盖缺口

事实：各模块有 if __name__ == '__main__' 自测，但不是自动化测试： 无 pytest、无 CI、无断言（靠 print 人工判读）、无测试用例目录。

具体缺口：

  • safe_eval() 沙箱没有独立自测（§2.3 的验证代码本次未执行）
  • 无并发测试：Core 的每线程连接与 BEGIN IMMEDIATE 写锁未做压力验证

（刻意避免"未验证"的断言，见下）

  • 无端到端自动断言（浏览器验证靠人工与截图）
  • web/app.js 无 JS 测试

影响：回归靠人眼。每次改动都可能静默破坏既有行为 —— 本项目撰写期间 已实际发生一次（见 §6.4）。

建议：迁移为 pytest + 断言；补并发用例（多线程同时转账同一账户， 断言最终余额与 ledger 一致）；把 verify_chain()、reconcile()、 check_tier() 的边界作为表驱动测试。

关于并发正确性：Core 采用「每线程一个 SQLite 连接 + BEGIN IMMEDIATE 写锁」 （L95、L253），设计上应能保证同一账户不会被并发扣成负余额，且 transfer 表对 idem_key 有 UNIQUE 约束作为兜底（建表语句中 UNIQUE (idem_key)，并在 IntegrityError 分支处理并发穿透）。 但这一点未经过压测验证，本文档不声称它已被证明。

5.10 演示环境的验证码明文回传

事实：request_strong_verification() 返回 demo_code（明文验证码）， 接口 /api/verify/request 直接下发给前端；界面上也显示"演示环境直接显示验证码"。

影响：强验证在演示环境中不构成真正的第二因子 —— 谁能调用该接口谁就能拿到验证码。 这是为了让评委能亲手跑通流程而做的刻意取舍，代码注释与界面均已标注。

建议：生产环境删除 demo_code 字段，只保留短信下发；若要保留演示能力， 用启动参数（如 --demo-mode）显式开关，并在日志中记录该模式的启用。

6.1 定时转账曾被静默降级为立即执行 —— 已修复

发现时的事实：意图解析器识别时间词并置位 slots['scheduled'] = True （agent/agent.py L310、L322），但 INTENT_ACTION['transfer'] 恒为 transfer.small， 且 _dispatch() 把 transfer.small / transfer.large / transfer.scheduled 归入同一分支直接调用 core.transfer()。

发现时的实测：

输入「每月给李娜转 300 元」
  propose 返回 type = confirm_required, tier = yellow
  确认执行后：李娜余额立即变化
  => 标记为「定时」的操作被立即执行了，没有真正的调度器

严重性判断：这不是"功能缺失"，而是语义相反的资金操作。 用户以为设了定时，钱当场出去。属于最危险的一类未实现 —— 报错至少是诚实的，静默错语义会直接造成损失。

修复：propose() 中新增显式拒绝（代码注释 L201-208，实测三例均被拒且余额不变）：

if intent.slots.get('scheduled'):
    self.audit.append('guard.unsupported_scheduled', session_id=self.id, text=text[:120])
    return {'type': 'refused', 'message': '定时/预约转账目前还没有实现调度器，我不能受理…'}
输入 propose 返回 余额变动
每月给李娜转 500 元 refused 无
明天给王强转 300 元 refused 无
预约下周给李娜转 100 元 refused 无

残留不一致：ACTIONS 中的 transfer.scheduled 登记项仍不可达 （无意图能映射到它，且带 scheduled 的意图在更早处已被拒绝）。 _summarize() 与 _details() 中仍有"（定时）"展示分支，同样不可达。

建议：若要实现定时转账，需持久化调度任务，且到期执行时必须重新走 完整的分级与确认流程（不能沿用创建时的授权 —— 那正是 §2.5 要防的时间差问题）。 若不做，建议删除 transfer.scheduled 登记项与"（定时）"展示分支， 消除登记表与实现的残留差异。当前状态（显式拒绝）在安全上已经是可接受的。

6.2 core.py 的"没有裸 UPDATE"表述范围不准确 —— 建议改措辞

代码事实：bank/core.py 模块文档（L28）写：

本模块不放行任何绕过路径 —— 没有 set_balance()，没有裸 UPDATE。

这个断言的适用范围需要区分：

  • 对资金变动成立：account.balance 只由 transfer() / reverse() 修改，

确认无 set_balance() 类接口。这是本项目最重要的一条架构约束（§1.3）， 且经代码检查确认成立。

  • 对非资金写不成立：orchestrator._dispatch() 中有 4 处直接 UPDATE。

它们都不是资金写，改的是状态字段：

动作 语句 级别 修改对象
subscription.cancel UPDATE subscription SET status="cancelled" … 黄色 订阅状态
card.freeze UPDATE account SET card_status="frozen" … 红色 卡状态
card.unfreeze UPDATE account SET card_status="active" … 红色 卡状态
card.limit_change UPDATE account SET daily_limit=? … 红色 限额参数

为什么这不构成"权限被绕过"：这 4 个动作都经过完整的 propose → 分级 → 确认/强验证 → execute 流程（实测：card.freeze card.unfreeze card.limit_change 均为红色且不给验证码时返回 need_strong_verification、状态未变；subscription.cancel 为黄色需确认、确认后生效）。绕过的是核心层的封装，不是权限分级。

真实影响（限于非资金写）：

  • 无幂等键：transfer() 有 idem_key 保证重复提交不重复扣款，

这 4 个动作没有。实际后果低（重复设为同一状态是幂等的），但机制上不一致

  • 不受对账保护：reconcile() 只核对余额与 ledger，不覆盖

card_status / daily_limit / 订阅状态

  • 事务边界不同：这些写入未包在 BEGIN IMMEDIATE 事务中

建议：修正 core.py 的措辞，明确约束范围。建议改为：

本模块是唯一的资金变动入口 —— 没有 set_balance()，
余额只能由 transfer() / reverse() 修改。
非资金类状态变更（卡状态、限额、订阅状态）由上层 _dispatch() 直接写库，
不经过本模块的事务与幂等保护。

同时建议把这些动作也收进核心层（提供 core.freeze_card() / core.set_limit() / core.cancel_subscription()），以获得统一的幂等与事务语义。

6.3 赛题级别定义与代码实现的对照

赛题规定：「小额转账（日累计 ≤ 1000 元）」为黄色，「大额转账（日累计 > 1000 元）」为红色。

6.4 撰写期间的真实事故：detect_injection 未定义导致全量崩溃

事实：在本文档撰写期间（2026-10-16 14:29），agent/orchestrator.py 被并发修改， 在 propose() 中新增了 hits = detect_injection(text) 调用，但 detect_injection 函数当时尚未定义。实测：

python -m py_compile agent/orchestrator.py   → 通过（NameError 是运行期错误）
hasattr(orchestrator, 'detect_injection')    → False
AgentSession.propose('我卡里还有多少钱')      → NameError: name 'detect_injection' is not defined

影响：propose() 对任何输入都抛异常，即全部对话功能不可用。

为何未在演示中暴露：运行中的服务进程持有编辑前的模块对象（内存中的旧代码）， 因此 GET /api/state 仍返回 200。重启服务即全量失效 —— 这个现象具有欺骗性，值得作为教训记录。

这件事的价值在于它证明了 §5.9 的测试缺口是现实风险，不是理论顾虑：

  • py_compile 通过 —— 语法检查抓不到未定义名称（它是运行期错误）
  • 服务 GET /api/state 仍返回 200 —— 因为进程持有编辑前的模块对象
  • 只有真正调用 propose() 才会暴露

也就是说，一个"所有静态检查都通过、服务看起来在正常响应"的状态， 实际上核心功能已经 100% 不可用。若项目有自动化测试 （哪怕只是一条 assert propose('查余额')['type'] == 'result'）， 这次事故在提交前就会被拦住。

建议：把 §7.4 的验证清单落成带断言的自动化测试，作为 CI 的第一步。 这是本文件所有建议中优先级最高的一条 —— 其他风险都是"某场景下有风险"， 而这个是"任何改动都可能静默破坏核心功能"。

6.5 card.limit_change 参数曾静默变成 0（严重）—— 已修复

根因：意图名与动作名混用。_build_params(intent, action) 中写的是

elif action == 'card_limit_change':      # ✗ 这是「意图名」

但 propose() 传入的是动作名 'card.limit_change'，因此该分支永不匹配。

后果链（每一环都不报错）：

用户：「把额度调到 10 万」
  ↓
_build_params 的 card_limit_change 分支不匹配 → params 里没有 limit
  ↓
确认卡明细显示「新上限 0.00 元/日」
  ↓
用户点确认
  ↓
_dispatch 用 `params.get('limit') or 5000000` 兜底
  → 但 params 里 limit 不存在，`None or 5000000` = 5000000
  → 而修复前的写法实际把限额设成了 0
  ↓
结果：单日限额 = 0 元 → 之后一分钱都转不出去

这是本项目最危险的一处缺陷：用户想提高限额， 结果是清零限额，而全过程没有任何报错。

修复：

  1. 统一按 action 判断（不再混用意图名）
  2. 0 是合法值，改用 is not None 而非真值判断 ——

否则"把限额设为 0"这个有意义的请求会被静默丢弃

  1. _dispatch() 拿不到 limit 时抛错而不是兜底默认值：
if action == 'card.limit_change':
    limit = params.get('limit')
    if limit is None:
        # 原先这里是 `or 5000000`，等于"你说改额度、但没说多少 → 我帮你设成 5 万"，
        # 方向完全随机。宁可报错，也不做一个用户没要求的资金参数变更。
        raise BankError('MISSING_LIMIT', '没有解析到目标额度，已取消调整。')
    if limit < 0:
        raise BankError('INVALID_LIMIT', '限额不能为负数。')

修复后实测：

初始单日限额: 50000.00 元

「把限额调到 10 万元」
  明细 = [('账户','A001'), ('新上限','100000.00 元/日')]
  不给验证码执行 → need_strong_verification（红色拦截正常）

「把限额调到 20000 元」+ 正确验证码
  → result「单日转出上限已调整为 20000.00 元。」
  限额 = 20000.00 元  ✓

「我要改额度」（未给金额）
  明细 = [('账户','A001'), ('新上限','—（未解析到金额，请勿确认）')]
  走完强验证后执行 → exec_failed / MISSING_LIMIT「没有解析到目标额度，已取消调整。」
  限额 = 50000.00 元（未变）✓

一般性教训（值得单独记）： "拿不到参数就兜底一个默认值"在资金类参数上是危险模式。 params.get('limit') or 5000000 这类写法的意图是"给个安全默认"， 但它实际做的是替用户决定了一个他没说过的资金参数， 而且方向可能完全相反（想提高 → 变成清零）。 对资金参数，缺失就应当报错。 这与 §2.1 的 DEFAULT_TIER = RED （未知动作按最高风险处理）是同一个原则：不确定时不要猜，尤其是往宽松方向猜。

残留小问题：propose() 阶段对缺 limit 的情况仍会生成确认卡 （明细显示"未解析到金额，请勿确认"），要等到执行阶段才失败。 更理想的做法是在 _missing_slots() 就拦住、直接追问用户。 不构成安全风险（有明确警告文案且执行被拒），属体验问题。

6.6 「三百五元」被解析为 305 而非 350（未修复）

事实：_cn_small('三百五') 返回 305，实现与其 docstring 一致：

"""解析中文数字，最多到千位。
…
例：三百五 → 3*100 + 5 = 305；三百五十 → 3*100 + 5*10 = 350。
"""

但 305 与中文口语习惯冲突 —— 口语「三百五」指 350。 实测：

_cn_small('三百五')   = 305
_cn_small('三百五十')  = 350
_cn_small('三百零五')  = 305
parse_amount_yuan('给李娜转三百五元')  = 305.0
parse_amount_yuan('给李娜转三百五十元') = 350.0

影响：若用户想说 350 元而说成「三百五元」，系统会转 305 元 —— 少转 45 元且不报错。与 §5.7.1 修复的两个金额错误（五百→5、 两块五→2）属同一类：金额静默错误。

为什么这一条未被 5.7.1 的修复覆盖： 5.7.1 的修复解决了"要求显式钱标记"和"百/千进位"两个问题， 测试集为 15 条金额用例。但「三百五元」这个"省略末位单位"的口语形式 不在测试集里，而它恰好是最常见的口语表达之一。 （撰写本文档时实测发现，故记录于此。）

当前状态：未修复。文档如实记录，不声称已解决。

修复建议（两种取向，需产品决策）：

  1. 按口语习惯解析：末位残留数字若前面出现过 百/千，

则视为下一级单位。即 三百五 → 3*100 + 5*10 = 350。 风险：「三百五」的确也可能被理解为"三百零五"的省略， 但这个理解在口语中远不常见。

  1. 老实拒绝：检测到"百/千后跟单个数字且无下级单位"时返回 None，

让用户补全为「三百五十元」或「三百五十」。 与 5.7.1 的"宁可多问一句"原则一致，更安全但不便。

倾向建议 2，理由与 5.7.1 相同：金额猜错的代价高于多问一句。 但若选 1，必须在测试集中补充「三百五 / 一千二 / 两千三」这类用例。

测试集缺口（应补入 §5.9 的自动化测试）：

「一千二」(1200? 1002?)   「两千三」(2300? 2003?)
「三百五」(350? 305?)     「一万二」(12000? 10002?)

这类"省略末位单位"的形式是中文金额的常见歧义区， 应作为表驱动测试明确固定预期值，而不是等用户报错。
