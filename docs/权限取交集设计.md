# 权限取交集设计（Scope Ceiling）

> 来源：OpenClaw 的身份与角色模型 —
> <https://docs.openclaw.ai/start/why-openclaw/identity-and-roles>
>
> 原文关键句：
> "A scope ceiling that is **intersected with** whatever connection auth granted,
> **never added to it**."
>
> 也就是：**权限只能取交集，不能相加。**
> 我们目前没有这一层。本文档说明为什么需要、怎么加、以及它挡住什么。

---

## 一、我们现在的权限模型只有一个维度

```
用户请求
   ↓
IntentParser 解析成 (action, params)
   ↓
check_tier(action, params, core, acct)   ← 只按"动作 + 金额/日累计"判三级
   ↓
绿 / 黄 / 红
```

**问题**：分级回答的是"这个操作有多危险"，但它没有回答
"**这个连接凭什么能发起这个操作**"。

这两件事是独立的：

| 问题 | 由谁回答 | 现状 |
|---|---|---|
| 这个操作多危险？ | `check_tier()` 三级分级 | ✅ 有 |
| 这个连接被允许做什么？ | **没有人回答** | ❌ 缺 |

**为什么现在没出事**：网页版里"能打开页面"隐含了"是账户本人"，
虽然没有正式的身份体系，但**攻击面是单一的**。

**为什么接 IM 渠道后必须补**：飞书应用的权限是**按应用授予**的，
一个只被授予"读取消息"权限的应用，其连接**不该能发起转账流程**。
即使后面还有确认与强验证挡着，**它本不该走到那一步** ——
多余的能力就是多余的攻击面。

---

## 二、交集模型

```
有效权限 = 连接授权权限 ∩ 会话分级上限 ∩ 动作所需能力
```

三层各自的含义：

| 层 | 例子 | 谁决定 |
|---|---|---|
| **连接授权权限** | 飞书应用只被授予 `read`；网页会话被授予 `read,write` | 渠道接入时的授权配置 |
| **会话分级上限** | 群聊会话只允许绿色动作；私聊允许全部三级 | 会话类型（见 IM 渠道设计 §四） |
| **动作所需能力** | `transfer.small` 需要 `write`；`account.balance` 只需 `read` | `ACTIONS` 注册表新增字段 |

**交集为空即拒绝**，且必须写审计事件。

## 三、实现方案（最小侵入）

### 3.1 给 ACTIONS 注册表加 `scope` 字段

```python
ACTIONS = {
    'account.balance': {'tier': GREEN, 'scope': 'read',  'desc': '查询余额'},
    'transfer.small':  {'tier': YELLOW, 'scope': 'write', 'desc': '小额转账'},
    'transfer.large':  {'tier': RED,   'scope': 'write', 'desc': '大额转账'},
    'card.freeze':     {'tier': RED,   'scope': 'write', 'desc': '挂失/冻结卡片'},
    ...
}
```

**未标注 `scope` 的动作按"未分类"处理，默认拒绝** ——
这是照抄 OpenClaw 的做法：

> "methods with no scope classification are **denied rather than allowed**"

### 3.2 分级判定前先做交集

关键顺序：**交集判断必须在 `check_tier()` 之前。**

```python
def authorize(action, granted_scopes, cap=None):
    """在分级判定之前先确认"这个连接有没有资格发起这个动作"。

    顺序很重要：先问"能不能"，再问"有多危险"。
    反过来会出现"已经算完了风险等级、才发现根本没权限"的尴尬路径，
    而且容易顺手把结果当成通过。
    """
    spec = ACTIONS.get(action)
    if not spec:
        return False, '动作未登记'
    need = spec.get('scope')
    if not need:
        return False, '动作未做 scope 分类，默认拒绝'
    if need not in (granted_scopes or set()):
        return False, '当前连接未被授予 %s 权限' % need
    if cap is not None and tier_rank(spec['tier']) > tier_rank(cap):
        return False, '超出本会话的分级上限'
    return True, 'ok'
```

### 3.3 三处调用点

| 位置 | 现在的行为 | 加什么 |
|---|---|---|
| `propose()` 分级之前 | 直接 `check_tier()` | 先 `authorize()`，不通过即 `refused` + 审计 |
| `execute()` 重算分级之前 | 直接 `check_tier()` | 同样先 `authorize()` —— **执行时必须再查一次** |
| IM 入口 | —— | 由 `channel_binding.scopes` 提供 `granted_scopes` |

**注意 `execute()` 也必须查。** 理由与"执行前重算分级"完全一样：
判定与执行之间存在时间差，这期间权限可能被回收（管理员撤销了渠道授权）。
只查 propose 不查 execute，就留下了一个与 §3.18 同类的绕过窗口。

---

## 四、默认值的选择

| 场景 | `granted_scopes` 默认值 | 理由 |
|---|---|---|
| 网页版（演示） | `{read, write}` | 现有行为不变，避免为了加这一层而破坏演示 |
| 飞书渠道 | 由 `channel_binding.scopes` 决定，**默认空前缀** | 未配即无权限 |
| 群聊会话 | `{read}` 且 `cap=GREEN` | 见 IM 渠道设计 §四 |

**默认必须保守**：新增渠道时如果忘了配 scopes，结果应该是"什么都不能做"，
而不是"什么都能做"。

---

## 五、它挡住的攻击

| 攻击 | 没有 scope ceiling | 加了之后 |
|---|---|---|
| 只读渠道发起转账 | 会走到确认卡（有强验证兜底，但已越界） | **在分级前就被拒** |
| 群聊里发"给某人转 500" | 归属不明却进入流程 | 群聊 `cap=GREEN`，直接拒 |
| 管理员撤销渠道授权后 | 已签发的会话仍可执行 | `execute()` 重查，拒绝 |
| 新增动作忘了配 scope | 默认放行 | **默认拒绝** |
