# IM 渠道接入设计（飞书 / 企业微信）

> 赛题要求：「用户可通过 **APP、IM 等渠道**与 Agent 联通。」
> 我们目前只有网页版。本文件设计 IM 渠道的接入方案，**重点是接入带来的新安全问题**。
>
> 参考对象：OpenClaw 的渠道设计（`/channels/pairing`、`/channels/access-control`、
> `/channels/bot-loop-protection`）。**它们的做法给了我们三条必须补上的防线。**

---

## 一、为什么 IM 渠道不是"把 HTTP 接口换个壳"

网页版有一个隐含前提：**能打开这个页面的人，就是账户本人**。
这个前提在浏览器里靠会话维持，虽然弱但方向是对的。

IM 渠道**没有这个前提**，反而引入了三类新攻击面：

| 新攻击面 | 具体情形 |
|---|---|
| **发送者不可信** | 任何人只要知道机器人账号就能给它发消息 |
| **上下文混入** | 群里其他人的消息会进入同一个会话，可能被当成指令 |
| **机器人互触** | 两个 bot 互相回消息形成死循环，把配额烧光 |

所以关键在于：**不能因为消息来自"我们自己的机器人"就默认可信。**

## 二、从 OpenClaw 学到的三条防线

来源：<https://docs.openclaw.ai/start/why-openclaw/identity-and-roles>、
<https://docs.openclaw.ai/channels/pairing>

### 防线 1：未配对发送者，拿到的是配对码，不是 Agent

> "With DM policy set to pairing, **unknown senders get a pairing code, not the
> agent**."

**这一条必须照做。** 否则任何人都能对着机器人说"给我转 500 元"，
虽然还有确认与强验证挡着，但**本不该走到那一步**。

我们的做法：陌生 open_id → 直接回一条配对码，**不进入意图解析**。
配对码由本人在 App 内确认后，该渠道身份与账户绑定。

### 防线 2：权限取交集，不能相加

> "A scope ceiling that is **intersected with** whatever connection auth granted,
> **never added to it**."

飞书应用被授予的权限（比如只读）与会话本身的分级是**两个独立约束**，
必须取交集。

**这条我们目前完全没有**（见 `docs/行业对标与参考更新.md` §5.2）。
在 IM 渠道上线前必须先补，否则会出现"一个只读渠道仍能发起转账流程"。

### 防线 3：机器人循环保护

> `/channels/bot-loop-protection`

同一会话内，若连续 N 轮双方消息不含人类输入特征，直接中止并告警。

## 三、接口设计

### 3.1 入站：飞书事件订阅

```
POST /api/im/feishu        # 飞书事件回调（含签名校验）
```

处理流程（**顺序不可调换**）：

```
1. 校验签名与时间戳        → 失败即 401，不解析内容
2. 取出 sender open_id
3. 查绑定表：
     未绑定  → 回配对码，结束（不进意图解析）
     已绑定  → 继续
4. 循环保护检查            → 命中即中止并写审计
5. 计算有效权限
     有效 = 渠道授权权限 ∩ 会话分级上限
     为空    → 拒绝，写审计 guard.channel_scope_denied
6. 进入既有两阶段流程
     propose() → 需要确认时回交互卡片
```

**注意第 1 步与第 3 步在意图解析之前**。这与网页版的原则一致：
**不可信输入不能进入解析器**。

### 3.2 出站：确认卡片

黄级与红级都需要用户在 IM 里确认。用飞书的**交互卡片**承载：

- 卡片正文 = 我们原本的"确认卡"内容（摘要 + 判定依据 + 明细）
- 卡片按钮 = 「确认执行」/「取消」
- **红级不放验证码输入框**，而是跳转到 App 或短信完成强验证 ——
  IM 消息本身**不是**一个可信的强验证通道（消息可被转发、截图）

**为什么红级不在 IM 里收验证码**：短信验证码在 IM 里输入，等于把
"持有手机"这个因子降级成"能看到这条消息"。这是**安全降级**，不能做。

### 3.3 配对表

```sql
CREATE TABLE IF NOT EXISTS channel_binding (
  id          TEXT PRIMARY KEY,
  channel     TEXT NOT NULL,          -- feishu | wecom
  external_id TEXT NOT NULL,          -- open_id / userid
  acct        TEXT NOT NULL REFERENCES account(id),
  scopes      TEXT NOT NULL,          -- 该渠道被授予的权限，逗号分隔
  status      TEXT NOT NULL,          -- pending | active | revoked
  pair_code   TEXT,                   -- 待确认时的配对码
  created_at  INTEGER NOT NULL,
  UNIQUE (channel, external_id)
);
```

`scopes` 是 §二防线 2 的交集来源。

## 四、群聊的处理（不做群聊转账）

飞书 / 企业微信里机器人常被拉进群。**我们决定：群聊只允许查询类动作。**

理由：群里"给某人转 500"这句话的**归属不明确** ——
是发指令的人要转，还是他在复述别人的话？在资金操作上，
**归属不明就不能执行**，这不是体验问题而是责任问题。

实现上很简单：群聊会话的有效权限被限制为绿色动作集合。

## 五、实施顺序

| 步骤 | 内容 | 前置 |
|---|---|---|
| 1 | **scope ceiling**（权限取交集） | 无 —— 这是渠道接入的前提 |
| 2 | `channel_binding` 表 + 配对流程 | 步骤 1 |
| 3 | 飞书签名校验 + 事件入口 | 步骤 2 |
| 4 | 交互卡片（黄级确认） | 步骤 3 |
| 5 | 循环保护 | 步骤 3 |
| 6 | 企业微信（同构，接口不同） | 步骤 4 |

**步骤 1 必须先做**：没有它，渠道接进来就是一个绕过点。
