# 行业对标与参考更新

> 赛题原文要求：「行业对标：参考 Revolut AIR（Revolut 推出的 AI 银行助手）」
> 并注明「可参考 OpenClaw 等开源智能体项目」。
>
> 本文档做两件事：
> 1. 把两个参考对象的**可核实事实**列出来；
> 2. 逐条对照本项目，**说明我们一致在哪、缺在哪**，并据此给出更新方向。
>
> **来源与可信度**：每条事实都标注了来源与可信度等级。
> 标「未证实」的条目**没有**被用来说明任何结论 ——
> 我不会为了让对比表好看而替对方编功能。

## 二、OpenClaw：可核实的事实

来源：<https://docs.openclaw.ai/start/why-openclaw/policy-as-code>、
<https://docs.openclaw.ai/start/why-openclaw/identity-and-roles>、
<https://docs.openclaw.ai/start/why-openclaw/the-trust-boundary>
（均在 URL 后加 `.md` 取到纯文本源文件，2026-10 读取）

### 2.1 核心主张：策略即代码，不是提示词

> "Permission modes, tool policy, and exec approvals as **code-enforced gates
> rather than prompt requests**"

这句话与本项目的主张**几乎逐字对应**。赛题要求"注入防御"，而 OpenClaw 给出的
答案和我们一样：**把约束放在代码里，而不是写在提示词里**。

它同时诚实地承认：code-based enforcement 本身不独特 ——
Claude Code、Codex、Goose 都这么做。它认为**独特之处在于"在多渠道助手里
做结构化的工具门禁"**。

### 2.2 审批绑定：与我们的凭证绑定同构

> "Exec approvals **bind an approved run to its exact command, cwd, environment
> hash, and content-hashed file operands**, and **deny on any drift after approval**."

这是 OpenClaw 版的"确认凭证绑定操作内容"。对照本项目的实现：

| 维度 | OpenClaw | 本项目 |
|---|---|---|
| 绑定对象 | 命令 + 工作目录 + 环境哈希 + 文件操作数哈希 | 动作名 + 结构化参数（`payload_hash`） |
| 漂移处理 | deny on any drift | `操作内容与确认时不一致（参数被改动），已拒绝` |
| 无审批通道时 | **deny by default** | 未登记动作判为红色；无 OTP 则 `need_strong_verification` |

**结论：我们在同一原理上做出了一致的选择，而且是独立得到的。**
这条对标可以直接写进答辩 —— 不是"我们抄了它"，而是
"我们和业界成熟的 agent 安全设计收敛到了同一个结论"。

### 2.3 参数派生的权限（比我们的做法更彻底）

> "Eight operator scopes — read, write, admin ... are **derived per request from
> the actual parameters before dispatch**, and **methods with no scope
> classification are denied rather than allowed**."

注意后半句：**没有做 scope 分类的方法，默认拒绝**。
这比我们更进一步 —— 我们是"未登记动作判为红色（需强验证）"，
它是"未分类直接拒绝"。

两种取舍都成立：金融场景里"高风险的先拦住再让人确认"通常比"直接拒绝"体验更好，
但它的做法在安全上更保守。

> "A scope ceiling that is **intersected with** whatever connection auth granted,
> **never added to it**."

**权限只能取交集，不能相加。** 这一条我们**没有对应实现**（见 §5.2）。

### 2.4 信任边界与沙箱

> "**Sandboxing is off by default.** ... The Docker and Podman default profile has
> **no network, a read-only root, all capabilities dropped, and a non-root user**."

> "Sandbox bind mounts are validated **twice**, once on the normalized path and
> again after resolving through the deepest existing ancestor, so
> **symlink-based bypass attempts are rejected**."

两点值得学：
1. **默认关闭沙箱，并把这件事明确写在文档里** —— 诚实交代默认姿态；
2. **双重校验防 symlink 绕过** —— 这与我们"白名单而非黑名单"是同一思路的两种应用。

### 2.5 多渠道（我们最大的差距）

OpenClaw 有独立的渠道文档，包含国内平台：
`/channels/feishu`、`/channels/wecom`、`/channels/wechat`、`/channels/qqbot`、
`/channels/telegram`、`/channels/whatsapp`、`/channels/slack` 等数十个。

它还专门有：
- `/channels/pairing` —— 未知发送者**收到配对码而不是拿到 agent**
- `/channels/access-control`、`/channels/bot-loop-protection`（防机器人循环）
- `/concepts/standing-intents` —— "常驻意图"，与本项目要实现跨场景联动的时序触发同源

**赛题也明确要求"用户可通过 APP、IM 等渠道与 Agent 联通"，而我们目前只有网页。**
见 §5.1。

## 三、Revolut AIR：能证实的部分

**必须坦白：我无法取得 Revolut 官方新闻稿与博客的正文**（两次均返回 HTTP 403）。
因此以下只列**能核实存在**的信息，不做功能推测。

| 事实 | 来源 | 可信度 |
|---|---|---|
| Revolut 发布了 AI 助手，名为 **AIR**，定位"money intelligence" | [revolut.com 新闻稿](https://www.revolut.com/news/revolut_enters_new_era_of_money_intelligence_with_launch_of_ai_assistant/)、[blog](https://www.revolut.com/blog/post/air-ai-by-revolut/) | 存在可确认，正文不可读 |
| AIR 在爱尔兰及欧洲推出 | [The Paypers](https://thepaypers.com/fintech/news/revolut-launches-ai-assistant-air-in-ireland-and-europe)（页面含 2026-09-03 日期与 `agentic AI`、`digital banking` 关键词） | 中 |
| 典型用法是**支出分析类提问**，例如"我今年在咖啡上花了多少" | [Frandroid 报道标题](https://www.frandroid.com/services/banque-en-ligne/3060895_combien-ai-je-depense-en-cafe-cette-annee-revolut-devoile-air-un-assistant-financier-pas-comme-les-autres) | 中 |
| AIR 与"agentic AI"定位相关 | The Paypers 关键词 | 中 |
| **它的权限分级机制、审批流程、多因子策略** | — | **未证实，不予引用** |

**⚠️ 一处需要你注意的时间异常**：The Paypers 页面显示的日期是 **2026-09-03**，
而当前系统时间是 **2026-10-16**。这说明 AIR 的欧洲上线距今仅一个月左右，
**属于非常新的产品**。这有两层含义：
- 评委大概率**没有深度使用过**它，所以对标时可以讲得比他们更清楚；
- 但反过来说，**拿它做"功能清单对比"的风险很高** —— 它可能还在快速迭代，
  今天写的对比明天就过时。所以本项目的对标重点应放在**设计取向**而非功能逐条比。

**可安全得出的结论（仅基于上表）**：
AIR 的重心在**对话式财务洞察**（你能问它，它给你分析和执行），
而本项目的重心在**执行前的权限约束**。两者不是同一层的东西 ——
AIR 解决"能不能听懂并办事"，我们解决"办之前凭什么拦住"。

## 四、对标结论：我们一致在哪

| 设计原则 | OpenClaw | 本项目 | 是否一致 |
|---|---|---|---|
| 约束写在代码里，不写提示词 | ✅ | ✅ | **一致** |
| 审批/确认绑定具体内容，漂移即拒 | ✅ | ✅（payload_hash） | **一致** |
| 无审批通道时默认拒绝 | ✅ | ✅ | **一致** |
| 权限按请求参数派生 | ✅ | ✅（金额 + 日累计动态抬级） | **一致** |
| 未分类动作不放行 | ✅（直接拒） | ✅（判红 + 强验证） | 一致（取向更宽松） |
| 沙箱白名单而非黑名单 | ✅（双重路径校验） | ✅（AST 节点白名单） | **一致** |
| 审计可追溯 | ✅（durable audit ledger） | ✅（哈希链，可定位篡改） | **一致** |
| 默认姿态写入文档 | ✅（明说沙箱默认关） | ✅（明说未实现项） | **一致** |

**一句话**：在"agent 安全怎么做"这个问题上，我们与 OpenClaw 收敛到了同一组结论，
而且是独立得出的 —— 这对答辩是**有利的论据**，因为它说明这不是拍脑袋的设计。

## 五、对标结论：我们缺在哪（按重要性排序）

### 5.1 🔴 渠道单一：只有网页，没有 IM

**赛题明确要求**："用户可通过 **APP、IM 等渠道**与 Agent 联通。"
OpenClaw 支持飞书 / 企业微信 / 微信 / QQ / Telegram 等数十个渠道。

**我们的现状**：只有网页版（手机银行界面 + 安全控制台）。

**为什么这是重要差距**：银行 Agent 的真实场景里，用户在 IM 里说一句
"给我妈转 500" 比打开 App 更自然。而且 IM 渠道会引入**新的安全问题**
（消息来源不可信、群聊里可能被他人注入、需要配对机制）——
OpenClaw 专门为此做了 `pairing`（未知发送者收到配对码而非拿到 agent）与
`bot-loop-protection`。

**建议更新**：优先做**飞书 Webhook 接入**（个人开发者可申请，门槛最低），
并复刻"未配对发送者不给 agent"的设计。这同时能覆盖赛题场景 1 与渠道要求。

### 5.2 🟠 权限只加不交：缺少 scope ceiling

OpenClaw：**权限只能取交集，不能相加**（`intersected, never added to`）。

我们目前没有"连接的授权范围"这一层概念 —— 所有动作只按三级分级判定，
不存在"这个连接本身只被授予了 read 权限"的约束。

**风险**：如果将来接入 IM 渠道，一个只读渠道的 token 理论上仍能触发转账流程
（虽然仍需确认 + 强验证，但**本不该走到那一步**）。

**建议更新**：给会话加一个 `granted_scopes`，`check_tier()` 之前先做交集判断。

### 5.3 🟠 缺少"未分类即拒绝"的严格模式

OpenClaw：未经 scope 分类的方法**直接拒绝**。
我们：未登记动作判为红色，仍给用户一次确认机会。

**这是有意的取舍**（金融场景"拦住并解释"体验更好），但**应该在文档里说明这个选择**，
而不是让它看起来像遗漏。建议加一个开关：生产模式走严格拒绝，演示模式走判红。

### 5.4 🟡 渠道级安全细节

- 未知发送者配对（我们有会话 ID，但没有"未配对不给 agent"的机制）
- 机器人循环保护（IM 场景下两个 bot 互相触发）
- 群聊里的注入风险（群里其他人说的话可能被当成指令）

### 5.5 🟡 跨场景联动的时序触发

OpenClaw 有 `standing-intents`（常驻意图）与 `automations`（cron 作业）。
赛题场景 6 要求"检测生日 → 当月锁定资金 → 生日前 2 天订购"，
本质就是常驻意图 + 定时触发。**我们正在实现这一场景**，应参考它的调度模型。
